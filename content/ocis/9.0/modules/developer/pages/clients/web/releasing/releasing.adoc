= Releasing
:toc: right
:toclevels: 3
:description: ownCloud Web is part of the oCIS monorepo and is released together with oCIS. Only the npm packages are published separately.

== Web Is Released With oCIS

ownCloud Web lives in the `web/` folder of the link:https://github.com/owncloud/ocis[oCIS repository]. It is not released on its own: the `web` service build runs `pnpm install && pnpm check:types && pnpm build` in `web/` and copies the result into the service assets, so every oCIS release ships the Web version of the commit it was built from.

There are no separate Web releases, Web versions or Web release branches. Web changes reach a release the same way as any other oCIS change, through `master` and the oCIS `stable-X.Y` branches. See the xref:release_life_cycle.adoc[oCIS release life cycle] for release types and schedule, and the xref:releasing_guide/releasing_guide.adoc[Releasing Guide] for the oCIS release process.

== Changelog Entries

For a user-facing Web change, add a changelog entry to the oCIS root `changelog/unreleased/` folder, based on `changelog/TEMPLATE`:

* The first line starts with the change type `Bugfix`, `Change` (breaking change), `Enhancement` (new feature) or `Security`, followed by a short title.
* The body describes the change, wrapped at 80 characters.
* The last section lists the PR and issue URLs, for example `+https://github.com/owncloud/ocis/pull/<number>+`.

Existing Web entries are named like `bugfix-web-embed-delegated-token-renewal.md` or `enhancement-web-bump-pinia.md`. Do not create or move versioned changelog folders, this is part of the oCIS release process.

In addition, PR titles follow link:https://www.conventionalcommits.org[Conventional Commits] as described in `COMMIT_CONVENTION.md`. Web changes usually use `web` as the scope, for example `fix(web): [OCISDEV-1572] show an error when a copy gets no answer`. PRs are squash-merged and release notes are generated from these titles with git-cliff.

== Translations

Web translations are synced with Transifex automatically by the nightly `Translation Sync` workflow (job `sync-web`), which opens a pull request with the updated translations. To update them manually, run the following from the `web/` folder:

[source,bash]
----
make l10n-pull   # pull the latest translations from Transifex
make l10n-write  # write them to the translations.json files
----

== Publishing the npm Packages

The following packages in `web/packages/` are published to npm individually. Each one has its own version in its `package.json`, the versions are not kept in sync.

[cols="1,2",options="header"]
|===
| Package Folder
| npm Package

| `babel-preset`
| `@ownclouders/babel-preset`

| `design-system`
| `@ownclouders/design-system`

| `eslint-config`
| `@ownclouders/eslint-config`

| `extension-sdk`
| `@ownclouders/extension-sdk`

| `prettier-config`
| `@ownclouders/prettier-config`

| `tsconfig`
| `@ownclouders/tsconfig`

| `web-client`
| `@ownclouders/web-client`

| `web-pkg`
| `@ownclouders/web-pkg`

| `web-test-helpers`
| `@ownclouders/web-test-helpers`
|===

To publish a new version of a package:

. Bump the `version` in `web/packages/<package>/package.json` and merge it into `master` with a regular PR.

. Create a signed, annotated tag `<package>-v<version>` on the merged commit and push it to `owncloud/ocis`:
+
[source,bash]
----
git tag -s -a web-pkg-v13.0.1 -m "web-pkg-v13.0.1" <merged-commit>
git push origin web-pkg-v13.0.1
----

. The `Release NPM packages` workflow (`.github/workflows/release-npm-packages.yml`) picks up the tag and:
+
* determines the package from the tag prefix and fails for an unknown prefix,
* fails if the version in the tag does not match the `version` in the package's `package.json`,
* builds the design tokens and, for `design-system`, `web-client`, `web-pkg` and `web-test-helpers`, the package itself,
* publishes the package with `pnpm publish --access public --tag latest`, authenticating with the job's GitHub OIDC token (`id-token: write`). No npm token is configured in the workflow.

Every publish sets the `latest` dist-tag, so the version just published becomes `latest`.

[WARNING]
====
Never push a bare `v*` tag (for example `v12.5.0`) for Web. Any `v*` tag triggers the oCIS release workflow (`.github/workflows/release.yml`), which builds and publishes an oCIS release with that version.

Do not use `web/dev/scripts/create_and_push_tags.sh` or `web/dev/scripts/bump_versions.sh`. They are leftovers from the standalone Web repository: the first one pushes such a bare `v<version>` tag, the second one assumes that all packages share a single version.
====
